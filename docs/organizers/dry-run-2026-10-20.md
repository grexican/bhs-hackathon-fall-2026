# Cold-start dry run, 2026-10-20

A fresh clone of the public kit (`57adf81`), followed only the way a new student on Windows would:
README → SETUP.md (install, onboard, AI check) → `/start` scripted parts (`npm run new-app`) → a tiny
Node app → `/connect` (`locker:connect`, `locker:project`) → `/ship` (`npm run deploy`). The hub was a
local copy (`LOCKER_URL=http://localhost:4402`, dev sign-in, no Railway or OpenRouter keys), so nothing
real was created. Deploy can't be simulated without Railway: the run stops at the deploy step.

Ranked by how likely each is to stop a student on Saturday.

## Blockers

1. **PowerShell blocks `npm` on a fresh Windows laptop.** Cursor's terminal is PowerShell, and
   `npm` resolves to `npm.ps1`. With Windows' default execution policy that fails with
   *"running scripts is disabled on this system"* before `npm run setup` even starts. The same applies
   to `npm i -g @railway/cli` and anything else typed in PowerShell.
   *Fixed in SETUP.md* (one-time `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned -Force`).
   **For lane B:** `doctor` should check it (`Get-ExecutionPolicy` is `Restricted`/`AllSigned` →
   print that one line), and the README install section should mention it.

2. **Git identity only inside the kit, so commits in the app fail.** Onboarding set `user.name` /
   `user.email` with plain `git config` (kit repo only). Every app in `apps/<codename>/` is its own
   repo, so on a laptop with no global identity, `/wrap` inside the app fails with
   *"Author identity unknown"*. *Fixed:* `/onboard` skill and `npm run onboard` now use `--global`.
   **For lane B (new-app.mjs):** with no identity, the app's first commit is authored as
   "Hackathon Student <student@example.invalid>". Either read the kit repo's identity
   (`git -C <kit> config user.email`) and pass it with `-c`, or tell the student to run `/onboard` first.

3. **The Railway CLI isn't installed by anything.** `npm run deploy` is the first time a student
   hears of it: *"The Railway tool isn't installed. Install it with: npm i -g @railway/cli (then open a
   new terminal...)"*. That's a global install (blocker 1 applies), plus a new terminal (often a
   Cursor restart, see 5), in the middle of `/ship` on demo day.
   **For lane B:** `doctor` should check `railway --version`. Better: add `@railway/cli` to the kit's
   devDependencies and have `locker.mjs` prefer `node_modules/.bin/railway(.cmd)`, so `npm run setup`
   covers it and nothing is global. (Its postinstall downloads a binary from GitHub: test it on the
   school wifi first.)

4. **A project whose setup failed was a dead end.** If Railway hiccups during `locker:project`, the
   hub marks the project `failed`. Re-running said *"The hub couldn't finish setting up this project.
   Tell an organizer"*, and the hub had no button for it either. *Fixed:* re-running
   `locker:project` on your own failed project now calls the hub's `/retry`, and the failure message
   shows the hub's reason and says to run it again (test added).

## Friction

5. **PATH after installing git/Node.** SETUP.md said "a new terminal may be needed". In Cursor a new
   terminal inherits Cursor's old PATH, so git/node stay "not recognized" until Cursor is restarted.
   *Fixed in SETUP.md:* quit Cursor completely, reopen, paste "continue setup from SETUP.md step 1".

6. **Node version said three ways.** `engines` and `setup.mjs` need 22.18+, `/onboard` said "22+",
   `.nvmrc` says `22` (nvm would happily pick 22.11, which can't run `kit/ai/cli.ts`). *Fixed* in
   `/onboard`. `.nvmrc` left as is (lane B's install area): `22.18` would be safer.

7. **Device name on the hub's connect page.** It shows `os.hostname()`, which on Windows is
   `DESKTOP-8F3K2LQ`. A student won't recognize it when checking "is this my laptop". Suggest
   `"<username>'s laptop (<hostname>)"`.

8. **`npm run setup` ends with "Next: `npm run onboard`"** while SETUP.md has the agent do onboarding
   in chat (`npm run onboard` waits for typed answers the agent can't give). Harmless when the agent
   follows SETUP.md, confusing when a student reads the terminal. Suggest: "Next: in Cursor, type
   /onboard".

9. **Install noise.** `npm install` prints two `npm warn deprecated` lines (node-domexception, glob 11)
   and every `npm run` prints `npm notice run …` lines. Not errors, but they look like errors to a
   first-timer. A one-liner in SETUP.md ("warnings are fine, only red ✗ lines matter") would help;
   `--loglevel=error` in `setup.mjs` would hide the deprecations.

10. **`/onboard` edits the kit's README** (a banner under the title). When organizers push kit
    updates and a student pulls, README.md is the file most likely to conflict. Suggest a separate
    `ME.md` or the app's own `docs/idea.md` instead.

## What worked well

- `npm run setup`: 6 seconds on a warm machine, clear step labels.
- `npm run ai -- ask fast "hi"` with no key: clean simulated reply, no stack trace.
- `npm run new-app`: clear output and next step.
- `locker:connect`: the code box, browser fallback link and "✓ Connected as …" are clear. The hub's
  `/connect` page now also takes a typed code on a phone.
- Error messages for a missing `.env`, a missing Railway CLI and a missing `start` script all say
  exactly what to run.

## v2: second cold start, same day (kit `83a52ae`)

Fresh clone of the public kit, then only what README / SETUP / the skills say: `npm run setup`,
`npm run doctor`, a branch, `npm run new-app`, the starter app in a browser, then `locker:connect`,
`locker:project`, `locker:status` and `locker:bring` against a local hub (dev sign-in, no Railway or
OpenRouter keys, so hosting can't be created and the deploy step can't run).

**Much better than v1.** Every v1 blocker is handled:
- `npm run setup` installs the Railway tool locally, runs doctor at the end, and took 25 s.
- doctor checks the PowerShell policy, the git identity and the Railway tool, with one fix line each.
- The README has a by-hand path and the PowerShell fix.
- A failed setup can be retried.

**What worked:**
- The starter (`npm run dev`):
  - prints its address and one request line per call;
  - the tap counter persists;
  - with `LOCKER_GATE=1` and `LOCKER_GATE_USER` in `.env` it says "Hi, Test Student!" with no hub;
  - "Ask the AI" with no key gives a clearly labelled simulated reply that says to connect first.
- No console errors at 390 and 1440 wide.
- `new-app quiz-buddy` explains how the name was made from the codename.
- `locker:bring` asks, lists, shows the ownership line and withdraws, all with clear next steps.

**Friction found, and what happened to it:**
1. **Fixed: `locker:status` showed a failed project as just "failed".** It gave no reason and no next step, while
   `locker:project` had printed the reason a moment before. It now prints "Setup didn't finish: <reason>"
   and, for the owner, "Try again with: npm run locker:project -- <codename>". Test added.
2. **Fixed: the tester Feedback button said "Thanks! The team will read it." when it wasn't sent.** Before
   /connect, feedback is only written to `data/feedback.jsonl` on the laptop. It now says "Saved on this
   laptop only (data/feedback.jsonl). After /connect it goes to the team."
3. **Codenames are global across the hub.** A student whose idea matches an earlier test project
   (`study-buddy` here) gets "Someone already took…" after building locally for an hour, and then has to
   rename the folder. Suggest `new-app` asks the hub whether the codename is free when the laptop is
   connected, or `/start` connects earlier. Organizers: archive test projects before Saturday so common
   names are free.
4. **The Ask-the-AI box and the Feedback button are commented out in `public/index.html`.** That's fine,
   and the comments explain it, but a student who never reads the HTML won't know either exists. `/start`
   and `/test-with-a-friend` turn them on; worth one line in the starter page text.
5. **Not testable locally: the deploy.** Without Railway keys on the hub, `locker:project` stops at "Hosting
   isn't set up on the hub yet". The hub has no simulated hosting mode, so the full connect → ship path can
   only be rehearsed on production. Rehearse it once on Friday with a throwaway codename, then delete
   that project from /admin.
